## The one number that decides the architecture

Your ceiling is **A$50/mo ≈ US$390/yr** of Anthropic spend.

| Architecture | Cost per retained user/yr | Users supported at A$50/mo |
|---|---|---|
| Current (per-user nightly generation) | ~$5.50 | **~70–90** |
| Hybrid pool | ~$0.30 (synthesis only) | **~1,000–1,400** |

Per-user generation gives you a free app that stops working at ninety users. The pool is not an optimisation — it is the thing that makes "free" mean anything.

The good news: at your budget the pool is cheap to build. **~4,800 entries ≈ US$38 one-off**, then ~US$2/mo in top-ups.

---

## The core design idea

**Pooling changes only how `daily_entries` rows get *filled*. It changes nothing about the domain model.**

You still write a real `daily_entries` row per topic per day. Notes still FK to it. Journal, synthesis, conclusion, export, delete — every read path is untouched. The only difference is that the row's content is *copied from a pre-generated pool entry* instead of *generated by a live model call*.

That keeps the blast radius small and means you can ship it behind a flag and fall back to the existing generator at any time.

**Bonus you get for free:** verse validation happens once, at pool-build time, not per user. Bad entries never enter the pool. Your ~18% Sonnet-retry waste disappears entirely — and for the first time you can actually *read the content before it ships*. For a devotional app where bad theology is the reputational risk, that alone justifies the change.

## Phase 2 — Circuit breaker (before a single free user exists)

Non-negotiable. A free app with an uncapped model bill is an unbounded liability.

```sql
create table public.spend_ledger (
  id            uuid primary key default gen_random_uuid(),
  occurred_at   timestamptz not null default now(),
  kind          text not null,      -- 'pool_build' | 'entry' | 'synthesis' | 'classify'
  model         text not null,
  input_tokens  integer not null,
  output_tokens integer not null,
  usd_cost      numeric(10,6) not null,
  detail        jsonb not null default '{}'
);
create index spend_ledger_month_idx on public.spend_ledger (occurred_at desc);

create function public.month_to_date_spend_usd() returns numeric ...
create function public.spend_cap_usd() returns numeric as $$ select 33.0; $$;  -- ≈ A$50
create function public.generation_allowed() returns boolean ...
```

Every Anthropic call in `generate-entry`, `synthesize` and the pool builder writes a ledger row from the response's `usage` block. Cheap, exact, and it finally tells you what Ponder actually costs instead of what a spreadsheet guessed.

**Degradation order** — it must never hard-fail:

1. Supporter per-user generation → falls back to pool
2. Free synthesis → "back at the start of next month"
3. Pool top-up → pauses
4. **Daily entries never stop.** The pool already exists on disk.

That's the real argument for pooling: a pooled app *degrades* under a spend cap. A per-user app just stops.

Alert yourself at 60% and 85% of cap.

## Phase 3 — The hybrid pool

### Schema (new migration)

```sql
create table public.entry_themes (
  id uuid primary key default gen_random_uuid(),
  slug text not null unique,
  title text not null,
  description text not null,
  created_at timestamptz not null default now()
);

alter table public.topics
  add column theme_id uuid references public.entry_themes (id),
  add column theme_confidence real;

create table public.entry_pool (
  id uuid primary key default gen_random_uuid(),
  theme_id uuid not null references public.entry_themes (id),
  day_index integer not null,          -- roughly where in a thread's life this fits
  entry_type entry_type not null,
  verse_ref text not null,
  book_number smallint not null references public.bible_books (book_number),
  chapter smallint not null,
  verse_start smallint not null,
  verse_end smallint not null,
  verse_text text not null,            -- validated at build time, never model output
  thought text not null,
  illustration text not null,
  ponder text[] not null,
  prayer_prompts text[] not null,
  song_title text, song_artist text, spotify_id text,
  reviewed boolean not null default false,
  retired boolean not null default false,
  created_at timestamptz not null default now()
);
create index entry_pool_pick_idx
  on public.entry_pool (theme_id, entry_type, day_index) where not retired;

create table public.entry_pool_seen (
  topic_id uuid not null references public.topics (id) on delete cascade,
  pool_entry_id uuid not null references public.entry_pool (id),
  used_on date not null,
  primary key (topic_id, pool_entry_id)
);
```

### Selection — `select_pool_entry(p_topic_id uuid, p_date date)`

1. Resolve `topics.theme_id`.
2. Exclude anything in `entry_pool_seen` for this topic.
3. Exclude verse refs already used on this topic (ever) and across the user's topics in the last 60 days — the existing rule, unchanged.
4. Pick `entry_type`: challenge if this topic's last 4 entries had none, else affirming. Preserves the 1-in-4 posture.
5. Order by `abs(day_index - thread_age_days)`, then random.
6. Copy the row into `daily_entries`, insert into `entry_pool_seen`, done. **Zero model calls.**

**Fallback chain:** no match → existing synchronous `generate-entry` path (still alive, now the exception rather than the rule) → existing fallback verse logic. Three layers deep, same as today.

### Classification

One Haiku call when a thread is created (~US$0.0005): thread title + description → theme slug + confidence.

- confidence ≥ 0.6 → pooled
- confidence < 0.6 → flagged for per-user generation, and the slug logged so you can see which themes you're missing

### Themes — start with 40

waiting · calling & vocation · provision & finances · grief · anxiety & fear · forgiving someone · being forgiven · marriage · singleness · parenting · doubt · identity · anger · envy · pride & humility · obedience · a decision · healing · ministry · church hurt · integrity at work · rest & sabbath · generosity · suffering · hope · patience · gratitude · purpose · transition & moving · illness (own) · illness (loved one) · estrangement · a habit you can't break · prayer life · dryness in scripture · sharing faith · leading others · conflict · contentment · starting again

### Pool depth strategy

- **Top 10 themes: 365 entries each** — long threads must not exhaust the pool.
- **Remaining 30: 120 each** — ~4 months, extend on demand.
- Total ≈ 7,300 entries ≈ **US$55–60** one-off on the Batch API. Comfortably inside one month's ceiling; build it over two months if you'd rather.
- Reuse the existing prompt and batch machinery. The builder is a script that fans out over `(theme, day_index, entry_type)` instead of `(topic, date)`.

⚠️ Fix the batch `custom_id` bug first — `:` is rejected by the Anthropic API. The pool builder will hit exactly the same wall the nightly job did 6–22 Aug.

### Curate

Add a `reviewed` flag and a simple admin list. Read the pool before you ship it. You have never been able to do this before.

## Phase 4 — The support layer

### What's free, forever

3 threads · daily entry · notes · topic journal · notifications · thread conclusion & looking-back · export · delete. **The entire core promise.** Nothing that makes Ponder *Ponder* is behind the support option.

### What supporters get

| Perk | Why it's fair |
|---|---|
| **Per-user generated entries** instead of pooled | Elegant inversion: supporters fund the expensive path and receive it. Honest, and it's the perk that actually costs money |
| 6 threads instead of 3 | Convenience, not the promise |
| Unlimited synthesis | Free tier: 1 per thread per 30 days, **and only after 5+ notes on that thread** — which is the right product rule anyway. Synthesis of nothing is noise |
| Song of the day | Pure extra |
| Supporter mark + running-cost panel | Transparency converts better than guilt |

### Products

Keep `ponder_annual` / entitlement `pro` — repurposed, not rebuilt. RC credentials on both stores are already valid ([[ponder-android-billing]]), prices anchored at A$15.99. Remove the intro offer.

Add a second RC offering `tips` with **consumables** (repeatable):

- `ponder_tip_small` A$4.99
- `ponder_tip_mid` A$9.99
- `ponder_tip_large` A$24.99

Consumables carry no entitlement — no server state to keep. Grant only the cosmetic supporter mark.

### Placement — this is most of the conversion

A button in Settings converts at ~0.05%. Gratitude moments convert 5–20× better:

- Immediately after a synthesis renders
- On the thread-conclusion looking-back screen
- Day 30 / 100 / 365
- After a note longer than ~200 characters
- Settings, permanently, low-key

### Copy

> Ponder is free, and it stays free.
> It costs about A$— a month to run.
> If it's been worth something to you, you can chip in.

**Never use the word "donate."** Money paid to a Pty Ltd is assessable income, not a donation — GST applies if you're registered, and it isn't deductible for the giver. Apple also reads nonprofit language closely under 3.2.1(vi). "Support" and "tip" are accurate and are exactly the words the guidelines use.

Apple is the merchant of record for AU IAP and handles GST at the point of sale — confirm the treatment with your accountant before the first payout.

### What to expect

Per 1,000 installs: ~80 retained → 2–4% supporter conversion → **2–3 subscriptions (~$7 net each) plus tips ≈ A$40–90/yr.**

That is an offset, not income. Set the expectation now so the number doesn't feel like failure later.

## Risks

| Risk | Severity | Handling |
|---|---|---|
| **Pool exhaustion on a long thread** | Medium | 365 entries for top 10 themes; per-user fallback past the pool's depth |
| **Pooled content feels generic** | Medium | 40 themes is fine-grained; users never compare feeds. Monitor, don't pre-solve |
| **Free→paid is effectively one-way** | High, accepted | Named once. You've decided; the pool is what makes it survivable |
| **Apple review** | Low | Free app + tip consumables + supporter sub is standard. No "donate"/charity language, no external payment links (prohibited outside the US storefront) |
| **Supabase costs** | Low | Not in the A$50 API ceiling. Watch row counts as the pool and `entry_pool_seen` grow |
| **Ledger drift** | Low | Write from the API response `usage` block, never an estimate |

---

## The summary

Going free is survivable, but only because you accepted the pool. Per-user generation at a A$50 ceiling gives you a free app that breaks at ninety users; the pool gives you one that holds a thousand-plus, degrades gracefully instead of failing, cuts your 18% retry waste to zero, and — for the first time — lets you read the devotional content before your users do.

The support layer will not fund it. Build it because some people will genuinely want to say thank you, and put it where gratitude actually happens.
